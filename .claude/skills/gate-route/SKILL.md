# 게이트 라우팅

상위 규칙은 CLAUDE.md §4 다. 이 문서는 그 판정 절차만 담는다.

## 흐름

```
queue/doing   워커 결과 수령 → /delegate-run 「결과 수령 시 확인」 통과
   ↓
queue/review  게이트① 정적 리뷰
   ├ pass → queue/qa
   └ fail → /failure-handling
   ↓
queue/qa      게이트② 동적 QA
   ├ pass       → queue/done
   ├ fail       → /failure-handling
   └ E2E 없음   → queue/qa 에 두고 사람 확인 대기 (자동 통과 금지)
   ↓
queue/done    Claude 가 커밋
```

정적과 동적은 서로를 대체하지 못한다. 하나가 통과해도 다른 하나를 건너뛰지 않는다.
게이트는 큐 파일 1건 단위로 태운다.

## 게이트① 정적 리뷰

### 담당 배정

| 위험도 | 리뷰어 |
|---|---|
| 고위험 — 아키텍처, 보안, 스키마, 데이터 손실 가능성, 다중 모듈 영향, 자격증명 | Codex |
| 저위험 — 단일 기능, UI, 타입, 문서, 기계적 리팩터링 | agy |

등급이 애매하면 한 단계 위로 올린다.

**셀프통과 금지가 위험도 배정보다 우선한다**(CLAUDE.md §4).
구현자와 리뷰어는 반드시 다른 주체다. 같은 워커라도 세션이 달라야 한다.
저위험 건을 agy 가 구현했으면 리뷰는 Codex 가 하거나 다른 fresh agy 세션이 한다.
고위험 건을 Codex 가 구현했으면 리뷰는 다른 Codex 세션이 한다.
Claude 는 오케스트레이션 전담이므로 직접 리뷰하지 않는다(CLAUDE.md §1).

리뷰는 읽기 전용으로 돌린다. 리뷰어가 코드를 고치면 그 순간 구현자가 되므로
판정 자격을 잃는다. 리뷰 브리프에 "파일을 수정하지 마라" 를 명시한다.

### 검증 명령

`verify_typecheck` / `verify_lint` / `verify_test` 세 명령은 **Claude 가 직접 실행**한다.
워커의 `checks` 필드를 그대로 믿지 않는다. 명령 원문과 출력은 `logs/<id>.log` 에 남긴다.
세 명령 중 하나라도 fail 이면 리뷰어에게 넘기기 전에 이미 fail 이다.

### 판정 기준

판정은 **pass 또는 fail 만**이다. "대체로 괜찮음" 은 판정이 아니다.

pass 조건 — 아래를 전부 만족해야 한다.

- 브리프의 완료 조건을 전부 충족
- 브리프의 범위 밖 파일이 변경되지 않음
- 검증 명령 3종 통과
- 명백한 결함 없음

fail 조건 — 하나라도 걸리면 즉시 fail.

- 빈 diff, 또는 브리프와 무관한 변경 (허위 보고 탐지가 최우선이다)
- `evidence` 가 명령 출력 원문이 아님
- 테스트 skip·only, 스냅샷 자동 갱신, assertion 삭제, 타입 우회
- 통과시키려고 구현이 아니라 테스트를 고친 흔적
- 미완성 구현, 하드코딩 스텁, TODO 잔존, 도달 불가 분기
- 스키마와 코드의 컬럼·필드 불일치
- `spec.md` 코딩 규약 위반
- 워커가 커밋·머지·태그·푸시를 함

### 산출물

리뷰어는 아래를 남긴다.

- `verdict`: pass | fail
- `findings`: `file:line — 문제` 목록. pass 면 빈 목록
- `[QA 인계]`: 사용자 동작에 영향을 주는 변경이면 시나리오 1~3줄. 없으면 "없음"

Claude 는 verdict 와 근거 한 줄을 `logs/<id>.log` 에 적는다.
게이트 로그 없이 완료라고 보고하지 않는다(CLAUDE.md §4).

## 게이트② 동적 QA

### 대상

사용자 동작에 영향을 주는 변경 — 화면 전이, 입력, 인증, 결제, 데이터 변경 등.
게이트①이 남긴 `[QA 인계]` 시나리오가 입력이다.

### 절차

- E2E 가 **있으면** 실행해 판정한다. 실행 명령은 `spec.md` 를 따른다.
- E2E 가 **없으면 자동 통과를 금지한다.** 큐 파일을 `queue/qa/` 에 둔 채
  사람 확인을 기다린다. "코드상 문제 없어 보임" 은 통과가 아니다.
- 순수 내부 로직·문서·비-UI 변경이라 QA 가 불필요하면 생략할 수 있다.
  **생략 사유를 `logs/<id>.log` 에 반드시 적는다**(CLAUDE.md §11).

### 주체 분리

구현자가 자기 코드를 QA 하지 않는다. QA 세션은 제품 코드를 수정하지 않는다.
테스트 작성·실행·증거 저장까지만이다. 실패가 나오면 구현자에게 되돌린다.

### 증거

실패 시 재현 절차와 출력 원문, 스크린샷·로그 경로를 남긴다.
증거 없는 "정상 동작 확인" 은 통과가 아니다.
검증하지 않은 항목을 통과로 표기하지 않는다. 미검증은 `[미검증]` 으로 명시한다.
QA 테스트 계정과 접근 금지 데이터는 `spec.md` 「운영 데이터 접근 범위」를 따른다.

### 배포 후 회귀

배포는 사람 승인 없이 하지 않는다(CLAUDE.md §7). 승인이 있어 배포한 경우,
배포 후 전체 회귀는 Codex 가 맡는다. 배포 명령·대상은 `spec.md` 를 따르며,
비어 있으면 배포하지 않는다.

## 반려 후

fail 판정의 재수정·재시도 절차는 `/failure-handling` 에 있다.
게이트 반려가 같은 원인으로 2회면 구현이 아니라 지시 자체를 의심한다.
